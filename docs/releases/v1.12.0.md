# PnP Bridge 1.12.0

## Fixed

- **A Day-N deployment that Catalyst Center reported as SUCCESS could have
  reached the switch with nothing at all.** The top-level `status` of a
  template deployment describes the *request*; the per-target outcome lives in
  `devices[]`, and CCC will report the deployment SUCCESS while its only target
  sits at `NOT_APPLICABLE` or `SKIPPED`. PnP Bridge trusted the top-level field,
  showed a green run, and patched the NetBox device to `active` for a switch
  that never received the config.

  Every target's status is now checked as well. A target that did not succeed
  fails the device with its `status` and `detailedStatusMessage`, and NetBox is
  left untouched.

## Added

- **The switch role is mirrored into Catalyst Center inventory.** After a
  successful claim, the role shown in wizard step 3 (`switchType`, taken from
  the NetBox device role) is mapped onto CCC's role enum — `ACCESS`,
  `DISTRIBUTION`, `CORE`, `BORDER ROUTER` — and applied with
  `roleSource: MANUAL` so an inventory sync will not overwrite it. The raw
  NetBox role name is also created as a CCC tag and attached to the device.

  This is best effort: the device is already onboarded at that point, so any
  failure is logged and shown in the Logs page but never fails Day-0.

## Known limitations

- The four inventory endpoints used for role and tag are the documented 2.3.7
  Intent API shapes but have not been confirmed against a live controller yet.
  That is why failures are non-fatal — check the Logs page after a run to see
  whether they were accepted.
- AAA / TACACS / RADIUS from Catalyst Center **network profiles** are not
  applied by PnP site-claim or by template deploy. Applying them requires a
  separate Provision step, which this release does not yet perform.

## Upgrade notes

- No schema change. `git pull && make image`, recreate the container.
