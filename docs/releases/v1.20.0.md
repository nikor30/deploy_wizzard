# PnP Bridge 1.20.0

## Diagnosis: why provisioning fails

The task tree from a live run splits the provision into two child operations:

- `Provision Devices: Assigning Devices to Sites` — **succeeds**
- `Provision Devices: Provisioning assigned Devices` — **fails, `NCHS20057`**

So the site is accepted (a floor is fine — 1.19.0's substitution was wrong and
was reverted), the device *is* assigned, and only the configuration push fails.

Per Cisco's base-automation troubleshooting guide, Catalyst Center fails a
provision when it detects **AAA CLI on the device that it did not push itself**
while AAA is defined in the network settings of the target site. A Day-0
onboarding template that configures AAA/TACACS/RADIUS puts exactly that on the
box, so provisioning then refuses to take ownership of it.

**The remedy is to remove AAA from the Day-0 onboarding template** and let
provisioning supply it from the site's network settings — which is the config
you want on the switch in the first place.

## Fixed

- **A batch child's own error code is no longer buried.** Children repeat the
  parent's generic "Batch Operation failed …" verbatim; that text is now skipped
  for children so the child's `errorCode` and `progress` lead the message.
- **`NCHS20057` and `NCSO20070` carry an actionable hint** naming the AAA
  conflict and the remedy.
