# PnP Bridge 1.24.0

## Fixed

- **Catalyst Center errors were being thrown away.** The client read only
  `message` and `response` from an error body, so anything else produced
  "failed with HTTP 400." with no reason. It now tries the known keys and falls
  back to the raw body — CCC's own words always survive.

- **Provisioning always sent POST.** `provision_wired_device` had a
  `reprovision` flag that nothing ever set. `POST` *creates* a provisioning; a
  device that already has one — every retry after the first, and anything
  provisioned once in the GUI — is rejected with `400`. A 400 now retries once
  as `PUT`, which is the re-provision.

## Day-N: why three templates fail

The banner applies, then:

- `IT_DayN_Port_Template` — rejected as invalid CLI (interactive prompt)
- `IT-DayN-Uplink_Conf` — *Connection to device … timed out using protocol ssh2*
- `IT_DayN_Vlan` — same timeout

The two timeouts are **collateral, not separate faults**: the port push takes the
switch's reachability with it, and everything after it cannot connect.

`ACCESS_PORTS` currently spans `TenGigabitEthernet1/0/37`–`1/0/47`, and several
of those show as `connected` in the switch's own interface status. Pushing access
configuration onto a live uplink or trunk is what drops the SSH session.

Worth checking in NetBox: are `Te1/0/37`–`1/0/47` really all client access ports?
Any that are cabled to another device, or that carry the management path, must be
marked as such (a cable, or 802.1Q mode `tagged`) so they are excluded.
