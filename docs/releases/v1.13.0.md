# PnP Bridge 1.13.0

## Fixed

- **Onboarded switches had no AAA, RADIUS/TACACS, DNS or DHCP config.** PnP
  site-claim assigns the device to a site and runs the Day-0 template; template
  deploy pushes template CLI. Neither applies the site's **network settings** —
  only provisioning does, and PnP Bridge never provisioned. A run could go
  entirely green and still leave the switch without a line of AAA config.

  After a successful claim the device is now provisioned to its site via
  `POST /dna/intent/api/v1/sda/provisionDevices`, and the task is polled to
  completion.

  A provision failure marks the device **failed** rather than successful. That
  is deliberate: silently calling it a success is what let the gap go unnoticed.
  The error names the cause and points at the escape hatch.

- **The CCC inventory role stayed unset when the Day-0 template had no role
  variable.** The role is known from the NetBox match either way, so it is now
  stored on the job device and used as a fallback. An edit in wizard step 3
  still wins.

## Added

- **Settings → Provisioning → "Provision to site after claim"** (default on).
  Turn it off if your controller does not expose the provision API — the switch
  will then need provisioning by hand in Catalyst Center.

## Upgrade notes

- **Schema change**: migration `0010` adds `job_devices.netbox_role`. It runs at
  startup; no manual step.
- `git pull && make image`, recreate the container.
- After upgrading, check Settings → Provisioning. If your build rejects the
  provision endpoint, the first claim will fail with the reason — turn the
  toggle off and provision manually while we correct the call.
