# PnP Bridge 1.17.0

## Fixed

- **Day-0 is clean again.** Provisioning after claim is now **off by default**.
  It was on from 1.13.0, and on Catalyst Center 2.3.7 the call is rejected with
  `NCSP11001`, so every Day-0 finished as a successful claim plus a red warning.
  Day-0 now behaves exactly as it did before 1.13.0. The toggle remains under
  Settings → Provisioning for retrying once the API call is proven.

- **Trunk ports and port-channel members are no longer treated as access
  ports.** A live Day-N run configured `Te1/0/37`–`Te1/0/47` and then aborted:
  Catalyst Center pushed `switchport mode access` at a port that is a trunk or
  bundled into a port-channel, the switch answered with a prompt instead of the
  config prompt CCC waits for, and CCC rejected the remainder of the push as
  invalid CLI — leaving the switch half configured.

  `ACCESS_PORTS` now also excludes interfaces with a NetBox `lag` (port-channel
  members) and interfaces whose 802.1Q `mode` is `tagged` or `tagged-all`.

## Known limitation — where TACACS, RADIUS and ISE config actually come from

These do not come from Day-N template variables. They come from the site's
**network settings** and the **network profile's** Day-N templates, and
Catalyst Center applies both during **Provision** — which is what the GUI runs
when you provision a device.

PnP Bridge's Day-N step deploys a template, which pushes that template's CLI and
nothing else. No amount of variable mapping on this side will produce AAA
config. Until `sda/provisionDevices` is accepted by the controller, provision
the device in the Catalyst Center GUI after Day-0 and let it apply the profile.

## Upgrade notes

- No schema change. `git pull && make image`, recreate the container.
- If you had provisioning enabled, it stays enabled — the new default only
  applies where the setting was never saved.
